# Audit de PROTOCOLE — 10/11/2026 (apps/perso v3.158.0)

Audit en lecture seule : rien n'a été modifié, ni dans le code ni sur le téléphone. Aucun appel
payant à l'IA.

**Méthode.** Mesures directes (tests, build, `npm audit`, `npm outdated`, stockage et journal
Android du téléphone) et trois relectures de code en parallèle (logique métier, écrans React,
partie Android). Chaque constat porte son niveau de preuve :
- **confirmé** : rejoué par un script ou relu dans le code jusqu'au bout ;
- **suspecté** : chemin plausible, pas observé.

**Non mesuré.** La vitesse de l'app sur le téléphone (il était en veille, puis une autre appli
était à l'écran). Les constats de performance viennent donc de la lecture du code.

## Ce qui va bien

- 254 tests verts, build propre.
- Aucun plantage ni blocage de l'app dans le journal Android.
- Batterie : 8 réveils depuis le dernier redémarrage du téléphone (repos, sauvegarde, brief).
- Android : aucun composant exposé sans protection, TLS normal partout, aucun secret dans les
  intents, clés secrètes absentes de l'export.
- Moteurs (recommandeur, créneaux, dépense, palier, score d'énergie) : aucun bug trouvé sur les
  dates locales, le changement d'heure ou les divisions par zéro.
- Code d'appel à l'IA conforme à l'API actuelle.
- Données du téléphone (copie du 09/11) : aucune séance en double, aucun jour fantôme.

## Lot 1 — Sécurité des données (à faire en premier)

1. **Modification d'une séance passée perdue après un retour dans l'app** — confirmé dans le code.
   - `apps/perso/src/screens/train/TrainTab.jsx:105` et `:109`, `apps/perso/src/App.jsx:339-353`.
   - Historique → ouvrir une séance → corriger → passer sur une autre app → revenir →
     « Enregistrer les modifications » : rien n'est enregistré, sans message.
   - Cause : au retour, l'app relit les séances (relecture de G3, 05/11). La séance en cours de
     modification est retrouvée par référence d'objet, qui ne correspond plus.
   - Correctif : la retrouver par `id`.
2. **Faille critique dans Capacitor Android 8.5.0** — signalée par `npm audit`
   (GHSA-rvm3-566m-v7fv, « du contenu distant peut être chargé à l'origine de l'app »).
   - Ce paquet est embarqué dans l'APK. Corrigé en 8.5.1 ; la 8.6.0 est disponible.
   - Les 17 autres alertes touchent des outils de développement, pas l'app installée.
3. **Stockage plein : l'échec est avalé** — confirmé dans le code.
   - `apps/perso/src/store.js:28-34` : `setItem` qui échoue → simple `console.error`.
   - Mesuré sur le téléphone : 0,92 million de caractères (journal alimentaire 466 000,
     conversations de Jeffrey 196 000, séances 191 000). Le plafond habituel d'une WebView est
     d'environ 5 millions ; il n'a pas été mesuré sur ce téléphone.
   - Au rythme actuel (environ 2,4 millions par an), le plafond serait atteint dans un an et demi
     environ.
   - Correctif : prévenir à l'écran quand une écriture échoue, et afficher la place occupée dans
     les Réglages.
4. **Restauration fragile** — chemin relu, minutage suspecté.
   - `apps/perso/src/screens/settings/SettingsPanel.jsx:191-198`, `ServerBackupCard.jsx:73-75`,
     `apps/perso/src/store.js:107-112`.
   - Pendant les 800 ms avant le rechargement, la synchro Health Connect peut réécrire poids,
     sommeil et pas avec l'état d'avant la restauration.
   - `importData` ne vérifie rien pour un fichier : une valeur `null` ou d'un mauvais type peut
     bloquer l'app sur « Chargement… », sans accès aux Réglages pour réimporter.
5. **Aucune limite d'erreur React** — confirmé.
   - `apps/perso/src/main.jsx:42-46`. Une erreur dans un écran donne un écran noir à chaque
     lancement, sans accès à la sauvegarde.
   - Correctif : un écran de secours avec « Sauvegarder hors du téléphone » et « Recharger ».

## Lot 3 — Fiabilité Android

16. **Réponse depuis la notification** — relu dans le code.
    - `BriefRunner.kt:105` : l'arrêt différé du service (150 s) n'est jamais annulé. Il peut
      couper la réponse suivante en plein appel.
    - `BriefRunner.kt:110` : au-delà de 55 s, la notification reste sur « … », sans bouton.
17. **Bouton Sync du widget sans garde-fou** — relu dans le code.
    - `SilentSyncActivity.kt`, `App.jsx:266-276`. Si la synchro ne finit pas, la fenêtre invisible
      reste ouverte et le widget tourne sans fin.
18. **Pont JEFFREY : le nom de l'appli appelante n'est pas vérifié** — confirmé dans le code.
    - `bridge/JeffreyBridgeService.kt:68`. Toute appli signée par la clé du Mac passe ; une
      autre de tes applis de développement est installée sur le téléphone.
19. **`allowBackup="true"`** — confirmé dans le manifeste.
    - Si la sauvegarde Google est réactivée, les clés secrètes y partent.
20. **Android 17** — suspecté.
    - La voix de Jeffrey app fermée passe par un service de type `shortService`
      (`AndroidManifest.xml:70-73`). `RestAudioService.kt:45-51` : un refus de premier plan
      mènerait à un plantage différé.
21. **Divers, gravité basse.**
    - Sauvegarde 14 h / 23 h : le réveil suivant n'est programmé qu'à la fin (`Backup.kt:112-121`).
    - FC repos calculée sur le fil de l'interface (`HealthNutritionPlugin.kt:40`).
    - `MediaPlayer` pas toujours libéré (`RestAudioService.kt:90-142`).
    - Chemins où un secret pourrait finir dans le journal en cas d'erreur d'en-tête
      (`BriefRunner.kt:84`, `:323`).
    - Une WebView neuve à chaque opération du pont (`JeffreyBridgeService.kt:123`).

Écarté après vérification sur le téléphone : la vibration de fin de repos. Les six de ce matin
ont été jouées.

## Performance (lecture du code, non mesurée)

- Analyse › Dépense recalcule tout à chaque rendu (`PerformanceTab.jsx:241-262`) : trois
  lectures du journal alimentaire, puis dépense, tendance et fenêtres.
- Nutrition : les habituels sont recalculés sept fois par rendu (`NutritionTab.jsx:541`), et
  l'onglet se dessine six fois à l'ouverture (`foodStore.js:36-46`).
- Chaque retour dans l'app recharge et réécrit tout, même si rien n'a changé
  (`App.jsx:339-353`, `:374`).
- Le carnet entier se redessine chaque seconde pendant un repos (`MuscuLogger.jsx:136`).
- Le code de l'app tient en un seul bloc de 820 Ko. Il est lu depuis le téléphone, l'effet est
  faible.

## IA

Le code est conforme. Améliorations possibles :
- Le secours est Haiku 4.5 (1 $ / 5 $ par million de tokens). Haiku 5.5 existe à 0,10 $ / 0,50 $ ;
  le passage demande de lire le guide de migration.
- Les lectures de cache sont comptées à 10 % du tarif d'entrée. Pour Opus 5.5, c'est 0,20 $ par
  million, soit 5 % : le coût affiché est un peu surestimé.
- Aucun tarif pour Fable 5.2 ni Haiku 5.5 dans la table : le coût serait estimé au tarif Sonnet.
- Un refus du modèle (`stop_reason: "refusal"`) n'a pas de message dédié.
- Photo d'un plat et Carte resto lisent du JSON dans du texte ; les sorties structurées de
  l'API le garantiraient (à vérifier à travers LiteLLM).
